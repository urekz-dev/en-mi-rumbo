# ADR 0008: Environments and deployment flow

- Status: accepted
- Date: 2026-10-11
- Owner: Alexis Zazueta

## Context

The team wants `dev.enmirumbo.com`, `stage.enmirumbo.com` and `enmirumbo.com`, and wants `dev` to be a single URL where any branch can be deployed by hand to look at it. The project is built in public, so previews need no protection beyond the admin panel. Wrangler environments create one Worker per environment, by default named `<name>-<env>`, with its own bindings, variables and secrets; bindings and variables are not inherited, while routes and triggers are. Custom Domains need exact hostnames, create their DNS record and certificate on first deploy, and fail when a record already exists on the hostname. Astro's Cloudflare adapter chooses the Wrangler environment at build time through `CLOUDFLARE_ENV`. Until the cut-over, the apex and `www` records of enmirumbo.com point to the prototype on Vercel. The domain's DNS is still at Namecheap and moving it to Cloudflare needs the registrar account, which only Jorge Pilo holds; until then no Custom Domain can be attached. When `workers_dev` is on, Version URLs are on by default too, and a path-based Access application does not cover them.

## Decision

Four environments. The deployed ones are identified as `dev`, `stage` and `prod` everywhere: Wrangler environments, Neon branches and Infisical environments. Local runs `astro dev` in workerd with PostgreSQL in Docker. `dev`: a Wrangler environment, deployed only by a manual GitHub Actions workflow (`workflow_dispatch`) where the person picks the branch; before deploying, the workflow resets the Neon `dev` branch from `stage`, applies the branch's migrations and seeds, and records branch and commit in the run summary and in the page footer. `stage`: deployed automatically on every merge to `main`. Production: deployed from a tag `vX.Y.Z` that also creates a GitHub Release; versions stay at 0.x until the cut-over, which is 1.0.0. Each environment sets its Worker name explicitly: `dev-enmirumbo`, `stage-enmirumbo` and `enmirumbo` for production. Until the zone is on Cloudflare they are served at `dev-enmirumbo.urekz.workers.dev`, `stage-enmirumbo.urekz.workers.dev` and `enmirumbo.urekz.workers.dev` (`urekz` is the account's `workers.dev` subdomain; a `workers.dev` hostname has a single label for the Worker, which allows only letters, digits and hyphens). Then `dev.enmirumbo.com` and `stage.enmirumbo.com` attach to `dev` and `stage` as Custom Domains and their `workers.dev` routes are turned off; production keeps only its `workers.dev` URL, with `noindex`, until the cut-over attaches the apex and `www`.

Every deploy builds for its target with `CLOUDFLARE_ENV=<env>` and deploys with the project's own Wrangler; no artifact is promoted between environments. Routes and Cron Triggers are declared inside each environment block, never at the top level, so nothing is inherited by accident: the hourly trigger exists only on `stage` and production. `preview_urls` is off in every environment, so no Version URL can bypass Access. No automatic previews per pull request. Non-production environments send `X-Robots-Tag: noindex` and a closed `robots.txt`, keep the admin behind Access, and use only fictional data. Absolute URLs, canonicals, Open Graph and the sitemap come from a per-environment site URL variable.

## Consequences

Two always-on Workers plus one that changes on demand; the Cron Trigger count stays within the free plan. Whatever is stored in `dev` is lost on the next deploy, by design. The first deploy of each environment needs a token allowed to create Workers; attaching the Custom Domains later also needs permission on the zone. Until the DNS move, the shared links of `dev` and `stage` are long `workers.dev` URLs, and they change once when the Custom Domains arrive. If two people compete for `dev`, Cloudflare Previews on `workers.dev` can be enabled later without changing this flow.
